# 卡带契约：格式版本与上限

> 参考 `sermon` 里那份 wrapper 路线图的核心判断：**卡带格式、受限 API、分辨率/色板这三件套必须在写第一份游戏内容之前定死**。否则第二阶段重构时，已经产出的每一款游戏都会报废。

这份文档只讲**不可变的那部分**。可变的东西（新增可选字段）在 `game-sdk.md` 里。

## 1. format_version：为什么必须有

`.hbx` 包目前没有格式版本号。这是唯一的硬缺口。

后果：将来改包结构（比如把 `game.js` 改成 `main.mjs`、把 `assets/` 平铺、加 `format_version` 之外的新目录）时，平台**无法区分新旧包**，只能二选一：

- 全部按新格式读 → 老包全部失效
- 保留所有旧分支 → 代码里永远有兼容补丁

所以 `format_version` 要在**第一个包发布之前**就写进 `game.json`。

**建议取值**：整数，从 `1` 开始，单调递增。含义是"包结构的代数"，不是游戏版本（游戏版本是 `version`，semver）。

```json
{
  "format_version": 1,
  "id": "author.game",
  "version": "0.1.0",
  "...": "..."
}
```

平台侧：

- 读到 `format_version > 当前支持的最大值` → 拒绝安装，提示"需要更新壳"
- 读到缺失 → 视为 `1`（向后兼容早期包）
- 读到 `format_version < 最小值`（未来某天废弃旧格式时）→ 拒绝并提示

**M2 定义包格式时必须先加这个字段**，加进去之后就不能再改了。

## 2. 资源上限：现在就该定

参考文档里有一句很实在的话：**不设上限的后果是内容一多就在电视上卡死**。

`package-format.md` 已经定了单包 ≤ 200MB、文件数 ≤ 4000。缺的是运行时侧：

| 上限 | 建议值 | 为什么 |
|---|---|---|
| 单游戏存档 | 1MB | 已在 SDK 里声明，需要平台侧真的强制执行 |
| 单帧逻辑预算 | 16ms（60Hz 下的一帧） | 超了就掉帧；平台已用"单帧最多补 5 步"兜底，但那是防死亡螺旋，不是防游戏本身慢 |
| 单包解压后内存峰值 | ≤ 2 × 包大小 | 已在 `compatibility.md` 声明，需要真实测试 |

**不做的事**：不在 v1 强制"每帧指令数"限制。JS 执行在浏览器里无法安全中断（没有 `Atomics.wait` 之外的手段，而 `SharedArrayBuffer` 需要跨域隔离响应头）。能做的是**测量并暴露**：`ctx.debug` 里加一个帧耗时读数，游戏作者自己看。

## 3. 受限 API：我们比参考文档宽，这是有意的

参考文档建议只开放 6 组：显示、输入、音频、时间、存储、随机。对照我们的实现：

| 组 | 我们的状态 | 差异 |
|---|---|---|
| 显示 | `ctx.ctx2d` 完整 2D 上下文 | **比参考宽得多**。给了整个 Canvas API |
| 输入 | 手柄/键盘/指针三层 | 比参考多（参考只要 4 向 + 2~4 动作键） |
| 音频 | `AudioContext` + 双总线 | **比参考宽**。游戏能自由合成 |
| 时间 | 固定 60Hz + `render(alpha)` | 一致 |
| 存储 | `ctx.storage` 同步读写 | 一致 |
| 随机 | 只有 `ctx.debug.seed`，没有内置 PRNG | **比参考窄**，缺一个已知种子的随机源 |

**为什么宽**：我们的目标不是 fantasy console 的极简复刻，而是"能跑中等复杂度 2D 游戏"的平台。收窄到 6 组的代价是很多游戏做不了，收益是跨端绝对一致——但我们的跨端只有 Windows 与 Android TV，两端都是成熟浏览器内核，一致性风险远小于"自定义字节码"的方案。

**代价要承认**：一旦给了完整 `CanvasRenderingContext2D`，就无法保证两个游戏看起来一致，也无法做"色板锁定"。这是设计选择，不是疏漏。

**基于这个判断，补一个缺口**：加 `ctx.random`，可定种子。理由不是"参考文档说要"，而是**没有它就无法复现 bug**——而这正是 `ctx.debug.stepFrames` 想解决的问题的另一半。

## 4. 美术规范：平台不定义，但工具要支持

参考文档把"色板 / 分辨率 / sprite 网格 / 描边 / 命名"列为开工前必须写死的 5 项。平台不该规定游戏长什么样，但应该让这些约束容易落地。

平台已有：`display.pixelArt`（最近邻）、`display.scale`（整数/等比）、逻辑分辨率声明。缺的是**色板**这一层——不做强制，但可以在 `game.json` 里留一个可选字段，货架与文档页能显示"这款游戏用 16 色"，工具（未来的 `hbx`）可以据此校验素材。

## 5. 文档收敛：4 份，不是 30 份

参考文档引用的实测数据值得记住：**30 份设计文档那一版在盲评里排最后**。多出来的 29 份买到的是可追溯性，不是更好的游戏。

游戏仓库应有的最小文档集：

1. **玩法一页纸** —— 核心循环 + 唯一核心动词
2. **系统表** —— 物品/数值/成长/经济，全部表格化
3. **设定圣经** —— 角色/世界观，可以边做边长
4. **美术规范** —— 色板 hex 表、分辨率、sprite 网格（必须最先定）

一份文档如果 AI 读完还不知道下一步写哪行代码，它就不该存在。

## 6. 垂直切片，不要一次写完

参考文档的第 6 阶段是最有价值的一条：**不要先写完所有系统再联调，而是一次只打通一条从输入到反馈的完整链路**。

对 Hearthbox 的具体含义：

- 第一版游戏应该能在 10 分钟内玩完，有开头有结尾
- 每一轮改动都留下一个**可玩**的小闭环，不是"能编译的空壳"
- 验收标准：**真跑起来并截图**，`typecheck` 通过不算

## 7. 不做的事

- **不改成 fantasy console 的极简 API**。理由见第 3 节。
- **不自研指令集模拟器**。模拟器核作为普通游戏包接入（`roadmap.md` 的"以后"）。
- **不做在线安装器**。M5 之前是静态文件 + hash。
- **不让 AI 一次性生成整个游戏**。见第 6 节。
