# 存档：只在本机

v1 不做账号、不做云同步。存档只存在当前设备的浏览器里，导出/导入文件是唯一的跨设备方式。

## 1. 存在哪

- IndexedDB 数据库 `hearthbox`，对象库 `saves`。
- 键是 `[gameId, key]`，值是游戏自己写的 JSON。
- `gameId` 来自 `game.json`，所以不同游戏互不可见。
- 单游戏上限 1MB。超了就是设计问题，不要靠压缩绕过。

Origin 决定 IndexedDB 的位置。换 origin（改 scheme、hostname、端口）等于换一套存档；见 D3。正式环境永远不要改。

## 2. 什么时候落盘

- 游戏通过 `ctx.storage.set` 同步写内存副本，平台约每秒合并落盘。
- `pause`、退出游戏、页面卸载时立刻 flush。
- 关键进度要立刻 `set`，不要攒到关卡结束——Android 可能直接杀进程。

## 3. 更新、卸载与存档

- 导入同 id 的新版本：只替换包文件，`saves` 不动；旧存档继续可用。
- 卸载游戏：只删包文件和 `installs` 记录，**默认保留存档**。
- 重新安装同一个 id：会读回原来的存档。
- 不同 id 的游戏永远看不到彼此的存档。

所以“删游戏”不等于“删进度”。要清存档，得显式去存档页处理。

## 4. 导出 / 导入

入口：货架卡片上的「存档」，或选中游戏后按 Select / Shift。打开 `/saves.html?id=...`。

导出文件是一个 JSON 信封：

```json
{
  "format": "hearthbox-save",
  "formatVersion": 1,
  "gameId": "me.my-game",
  "gameVersion": "1.0.0",
  "savedAt": "2026-10-23T12:00:00.000Z",
  "data": {
    "state": { "level": 3, "coins": 120 }
  }
}
```

规则：

- `gameId` 必须与目标游戏一致，不能把 A 的存档导进 B。
- `data` 是该游戏在 `saves` 里的全部键；导入会**整体替换**这些键，不是合并。
- 导入前会提示版本差异；版本不同不保证能读，游戏自己负责迁移。
- 导入是单个 IndexedDB 事务：失败就回滚，旧存档不动。
- 文件超过 1MB、格式不对、危险键（`__proto__` 等）都会被拒绝或跳过。
- 存档是数据，不是代码；导入不会执行任何东西。

导出/导入只走本地文件：PC 下载 JSON，电视用 U 盘或文件选择器。没有上传，也没有云端自动同步。

## 5. 明确不做

- 账号、云存档、跨设备自动同步。
- 后台上传存档、遥测。
- 存档市场或自动下载别人的存档。
- 跨游戏转移存档。

以后如果做云同步，也只会在现有信封上增加传输层，不改变“存档按 gameId 隔离、只由平台写”的规则。
