# 扩展架构：可调项与插件

> 核心判断：**金手指、游戏设置、成就是同一件事。** 设计一套，不是三套。

## 1. 为什么合并成"可调项"

三者表面不同，结构完全一样：

| | 谁声明 | 谁渲染 | 谁持久化 | 生命周期 |
|---|---|---|---|---|
| 金手指 | 游戏 | 平台 | 平台 | create 声明 → 退出落盘 |
| 游戏设置 | 游戏 | 平台 | 平台 | 同上 |
| 成就/统计 | 游戏 | 平台 | 平台 | 同上 |

差别只有一个：**出现在哪个面板**。所以用一个 `scope` 字段区分，而不是三套 API。

## 2. 数据模型

```ts
interface OptionBase {
  id: string;            // 稳定，发布后不改
  name: string;          // 玩家看到的名字
  description?: string;
  scope?: 'cheat' | 'setting' | 'status';   // 缺省 cheat
}
```

三种 `kind`：

| kind | 控件 | 必填 |
|---|---|---|
| `boolean` | 复选框 | 无 |
| `number` | 滑杆 | `min` / `max` / `step` / `defaultValue` |
| `choice` | 分段按钮 | `choices` / `defaultValue` |

**为什么强制给范围**：不给范围就没法生成 UI，也没法防止游戏读到 `1e9` 这种把平衡和存档都搞坏的值。声明时校验，写错立刻抛错，不等到玩家拖滑杆才发现。

## 3. 值的三层保护

```
UI 层     range 输入天然夹在 min/max
API 层    setOption 再夹一次（防止调用方绕过 UI）
读取层    读回来时再归一化（防止旧存档的超范围值）
```

第三种最重要：**游戏修改了范围，玩家旧的设置值可能越界。** 比如上一版上限 10、玩家调到 10，新版收到 3 —— 读回来必须是 3，不是 10。

## 4. 平台不写死任何一条

游戏声明三条，对应面板就显示三条。测试里这是硬断言，不是"看起来差不多"。

平台侧唯一知道的是 `scope` 和 `kind`，完全不知道"移动速度"是什么意思。

## 5. 未来可能加什么（已经预留）

### 5.1 新的 scope

现在三种够用。以后可能加：

| scope | 用途 | 需要的额外字段 |
|---|---|---|
| `accessibility` | 色盲模式、字号、闪烁减弱 | 无，复用现有三种 kind |
| `audio` | 独立音量、字幕 | 无 |
| `multiplayer` | 房间设置 | 无 |

**加 scope 不需要改平台代码** —— `byScope()` 已经是通用的，面板也是同一套渲染。

### 5.2 新的 kind

| kind | 控件 | 什么时候需要 |
|---|---|---|
| `text` | 输入框 | 玩家名、关卡种子 |
| `keybinding` | 按键捕获 | 自定义键位 |
| `color` | 取色器 | 主题色 |

`text` 和 `keybinding` 是**最可能先要的**。加它们需要改 SDK 的 `OptionKind` 联合类型和面板的 `OptionRow` 分支，各约 20 行。**不需要改变数据模型**（值已经是 `boolean | number | string`）。

### 5.3 联动与依赖

"选了困难模式就禁用某些金手指"这类需求。

现在不做，因为它会让数据模型复杂（需要表达式求值、循环依赖检测）。真需要时，最小方案是加一个 `enabledWhen?: (read: (id) => OptionValue) => boolean`，由游戏自己写判断函数，平台只负责调用。

## 6. 三类"插件"，别混成一个机制

你的直觉对：金手指确实像个插件。但"插件"这个词在三种场景下差别很大：

| 类型 | 谁提供 | 谁消费 | 例子 |
|---|---|---|---|
| **能力声明** | 游戏 | 平台渲染 | 可调项（金手指/设置/成就） |
| **平台扩展** | 第三方 | 平台调用 | 新输入源、新存储后端 |
| **内容包** | 第三方 | 游戏自己加载 | 关卡包、MOD |

### 6.1 能力声明（已实现）

就是本文说的这套。游戏声明，平台渲染。

**为什么这是对的形态**：游戏代码本来就在平台进程里跑，它声明什么平台立刻知道，不需要"加载"。硬套动态加载、注册表、生命周期只会增加复杂度，收益为零。

### 6.2 平台扩展（没做，也不该现在做）

设想界面：

```ts
// 平台提供注册点
host.registerInputSource(factory);
host.registerStorageBackend(factory);
```

**现在不做的理由不是"难"，是"没第二个实现"。** 没有第二个实现时，接口形状只能靠猜。猜错的接口比没有更糟 —— 因为一旦发布，改它就要破坏兼容。

什么时候做：真的出现"第三方写的输入源"（比如某个特殊手柄厂商）或"第三方存储后端"（比如接 NAS）时。

### 6.3 内容包（没做）

游戏自己定义格式、自己加载、自己校验。平台不参与。

**为什么平台不该管**：MOD 的安全边界、版本兼容、依赖排序，每个游戏都不一样。平台硬定一套格式，只会限制游戏。

## 7. 安全边界（必须说清）

**`ctx.options` 是只读接口，但这不是安全机制。**

游戏代码在浏览器里跑，它完全可以绕开 `ctx` 直接改自己的内部变量。平台能做的是：

- 状态存在自己的库里，游戏读不到别的游戏的
- `set` 只在平台侧（面板、`session.setOption`）
- 声明时校验，防止游戏写出坏数据

**这是"约定 + 便利"，不是"边界"。** 真正需要强隔离时（第三方不可信游戏），路是 iframe 沙箱 + postMessage，见 `architecture.md` 第 7 节。那是 v2，代价很大。

## 9. 一个已知短板

**面板只能用鼠标或键盘 Tab 操作，手柄不行。** 电视上没有鼠标，这确实是硬伤。

补它需要空间焦点算法（`decisions.md` D10 已经定了方案，约 200 行）。M3 一起做。

在那之前，电视上只能靠键盘（如果电视接了 USB 键盘）或直接用 PC 开发。
