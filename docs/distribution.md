# 分发与更新需求

> 状态：设计稿，待评审。**M2 开工前必须先定这份。**
>
> 这份文档回答三个问题：游戏怎么进来、怎么更新、玩家用起来什么感觉。

## 1. 现状与目标

### 现在有什么

- 平台能在 PC 浏览器里跑，货架上有内置演示游戏
- 能直接读工作区里其他游戏目录（开发用）
- **没有**：安装、下载、更新、卸载

### 目标形态

Windows 上装一个 `.exe`，打开就是货架，点一下游戏就能玩，不用管文件在哪。

```
玩家视角：
  安装 wrapper  →  打开  →  看到货架  →  点游戏  →  玩
                                    ↑
                          游戏从哪来？下载。

开发视角：
  写完游戏  →  hbx pack  →  上传到源  →  玩家那边刷新就能更新
```

## 2. 游戏从哪来：三种来源，一套机制

**统一抽象成"源"（source）**，不管是本地目录、局域网还是公网。

| 源类型 | 地址形式 | 典型用途 |
|---|---|---|
| 内置 | 打包进安装包 | 平台自带演示、离线兜底 |
| 本地目录 | `file://` 或安装包内的目录 | 开发时直接读，不用打包 |
| 局域网 | `http://192.168.x.x:8080` | 家里 NAS 放游戏，电视直接下 |
| 公网 | `https://games.example.com` | 正式分发 |

**同一个源协议**：一个 `catalog.json` + 若干 `.hbx` 文件。局域网和公网只是地址不同，代码路径完全一样。

### 2.1 为什么局域网也要走 HTTP，而不是直接读文件

技术上 Windows 可以读 `\\NAS\games\a.hbx`，但：

- Android TV 读 SMB 需要额外库，且权限模型复杂
- 文件路径在不同机器上不一样，没法在游戏清单里写死
- HTTP 有个好处：**能加缓存、能断点续传、能限速**

所以局域网就是"一个 IP 的 HTTP 服务器"。NAS 上开个静态文件服务，或者用 `hbx serve` 起一个。

### 2.2 玩家怎么加一个源

```
设置 → 游戏源 → 添加
  [ 名称 ]  家里的 NAS
  [ 地址 ]  http://192.168.1.10:8080
              ↓
        拉取 catalog，显示"找到 12 个游戏"
              ↓
        [ 添加 ]
```

**首次添加要确认一次**：显示源的签名公钥指纹，玩家确认后记住（TOFU）。之后公钥变了就拒绝，因为那意味着有人在中间替换。

## 3. 游戏怎么装进来

### 3.1 安装流程

```
玩家点"安装"
  → 从 catalog 拿 url / size / sha256
  → 流式下载，同时算 sha256
  → 比对 hash 与大小
  → 解压到内存，逐项校验路径、文件类型、game.json
  → 单个 IndexedDB 事务写入
  → 状态 ready，货架出现"开始"
```

**任何一步失败都不留残骸**：事务回滚，旧版本不动。

### 3.2 进度反馈

下载中必须显示：

```
[████████░░░░░░░]  52%   3.2 MB / 6.1 MB
```

超过 3 秒没有任何进度就是体验事故。所以：

- 进度按**已下载字节**算，不按文件数
- 网速慢时也要每秒刷一次，哪怕数字没变
- 失败要能"重试"，不能只显示个红叉

### 3.3 空间不够怎么办

安装前检查可用空间。不够时明确告诉玩家：

```
需要 120 MB，当前只剩 40 MB
[ 清理空间 ]  [ 取消 ]
```

不要等到装到一半才失败。

## 4. 更新

### 4.1 三个层次的更新

| 更新什么 | 怎么做 | 玩家感知 |
|---|---|---|
| **wrapper 本身** | Windows 安装包 / PWA | 提示"有新版本" |
| **货架清单** | 定时拉 catalog（几十 KB） | 无感 |
| **游戏包** | 下载新 `.hbx` | 货架卡片上出现"可更新" |

### 4.2 游戏更新

```
货架启动时  拉一次 catalog
每 6 小时   再拉一次（游戏运行中不拉，避免打扰）
发现新版    卡片角标"可更新"，不自动下载
玩家点更新  下载 → 校验 → 装新的 → 旧的留作 previous
确认能启动  才删更旧的
```

**关键决定：不自动更新游戏。**

理由：自动更新会在玩家玩到一半时改变行为，也可能引入新 bug。让玩家自己决定什么时候更新，尤其是本地存档可能受影响的版本。

### 4.3 回滚

每个游戏保留**一个**旧版本。设置页有"还原上一版本"。

保留一个而不是多个：占空间，且玩到第三版还退回第一版的情况几乎没有。

### 4.4 wrapper 自身更新

Windows 上：

| 形态 | 更新方式 | 体验 |
|---|---|---|
| PWA | 浏览器自动更新 Service Worker | 最好，无感 |
| 安装包（Tauri） | 内置更新器，下载新 exe 后重启 | 需要一次重启 |

**Windows 已经选 Tauri（D23）**：v1 交付 NSIS 安装包与绿色版 exe。PWA 不再作为主路径，但同一个 `apps/shell/dist` 仍可放到 HTTPS 静态服务上直接用浏览器打开。

Tauri 的代价是签名、更新器和"更新中途被杀"的兜底要自己做：当前没有接自动更新，覆盖安装即可；没有 Authenticode 证书时 SmartScreen 会提示未知发布者。
- 要签名证书（否则 Windows 会警告）
- 更新失败可能让应用起不来，需要"更新失败自动回滚"的逃生舱

### 4.5 更新的安全底线

- 只从已添加的源更新，不因为 catalog 里多了个 url 就去下载
- 每个包必须校验 sha256，不匹配就拒绝
- 更新失败不能让游戏变得不可用（保留 previous）
- **不在游戏运行时替换文件**，等回到货架

## 5. 卸载

```
设置 → 已安装 → 卸载
  [x] 同时删除存档        （默认不勾）
  [ ] 同时删除金手指设置  （默认不勾）
```

**默认保留存档与设置**：玩家重装之后还想接着玩。删存档要显式勾选。

## 6. 产品复核：站在玩家角度

### 6.1 第一次使用

理想路径（从双击 exe 到玩上）：

```
双击 exe          ← 1 秒
看到货架          ← 2 秒（含内置演示游戏）
按 A 开始玩        ← 0 秒
```

**第一次不需要联网**。内置一个演示游戏，让人立刻明白这是什么。

如果第一次打开是空货架、还要先配网络，大部分人会直接关掉。

### 6.2 只有手柄能不能走完全程

这是电视上的硬要求。逐项检查：

| 操作 | 手柄能做吗 |
|---|---|
| 浏览货架 | 能（方向键） |
| 进入游戏 | 能（A） |
| 暂停 / 退出 | 能（start+select 长按） |
| **打开金手指面板** | **不能**（面板里没有焦点导航） |
| **调滑杆** | **不能** |
| 加游戏源（输网址） | **不能**（要打字） |

**前三个是必须的，后三个现在是缺口。**

- 金手指面板的手柄导航：M3 做，约 200 行
- 加游戏源需要打字：这个只能靠键盘，或者做"扫码/输 IP 的简化界面"

**产品判断**：如果目标用户是"家里人自己玩"，加源这种一次性配置可以在 PC 上做好，不用在电视上做。这可以接受。

### 6.3 断网了会怎样

| 场景 | 期望行为 |
|---|---|
| 已装游戏启动时断网 | **正常玩**，不检查网络 |
| 货架刷新时断网 | 用上次缓存的 catalog，显示"离线" |
| 更新到一半断网 | 旧版本仍可玩，下次重试 |
| 全断网且没装游戏 | 至少能玩内置演示 |

**"已安装的游戏永远能玩"是底线。** 不能因为连不上服务器就打不开。

### 6.4 一个人玩 vs 一家人玩

现在只支持单机。多人同屏（两个手柄）在 SDK 里已经支持（`players` 数组长度 4），但没游戏用。

真正的多人在线不做，因为要服务器、要账号，和"自娱自乐"的定位冲突。

### 6.5 玩家会不会困惑的几个点

| 可能的困惑 | 对策 |
|---|---|
| "这些游戏哪来的？" | 货架底部显示当前源名称 |
| "为什么这个游戏是灰的？" | 卡片上写明原因（未安装 / 不兼容 / 需更新壳） |
| "我删了会不会丢存档？" | 卸载对话框里明确写"存档会保留" |
| "更新会不会覆盖我的进度？" | 更新不动存档，文档里写清 |

## 7. 技术选型的取舍

### 7.1 Windows 壳：PWA 还是 Tauri

| | PWA | Tauri |
|---|---|---|
| 安装 | 浏览器菜单"安装" | 下载 exe |
| 更新 | 自动 | 需要更新器 |
| 签名 | 不需要 | 需要证书 |
| 开机自启 | 不能 | 能 |
| 全屏无边框 | 有地址栏（可全屏隐藏） | 完全控制 |
| 体积 | 几 MB | 安装包约 1MB，exe 几 MB（复用系统 WebView2） |

**Windows v1 用 Tauri**（decisions.md D23）：独立安装包/卸载入口、稳定 origin、Gamepad API 在 WebView2 里可用，资源占用仍远低于 Electron。代价是 WebView2 依赖（安装包补装）、代码签名和更新器要另做；这些不阻塞 M4/M5 的产物交付。

### 7.2 存储：IndexedDB 还是文件系统

现在用 IndexedDB，单个数据库有配额限制（通常是磁盘的一部分）。

| | IndexedDB | 文件系统 |
|---|---|---|
| 容量 | 受限（浏览器配额） | 几乎无限 |
| 大文件 | 慢 | 快 |
| 实现 | 已有 | 需要 Tauri/原生 |

**200MB 以内的包用 IndexedDB 够用**（`package-format.md` 已经定了这个上限）。超过时再加文件系统后端，`PackageStore` 接口已经预留。

## 8. 落地顺序

按"玩家能获得价值"的先后排，不是按技术难度：

| 阶段 | 做什么 | 玩家能得到什么 |
|---|---|---|
| 1 | 坦克游戏移植进平台 | 有一个真的能玩的游戏 |
| 2 | `hbx pack` + 本地 catalog | 能把游戏打包、本地装 |
| 3 | 局域网源 + 安装器 | 家里 NAS 上的游戏能装 |
| 4 | 更新 + 回滚 | 游戏能升级 |
| 5 | PWA 安装 | Windows 上一个图标点开 |
| 6 | 公网源 | 不在家也能装 |

**每一步都必须能玩到东西**，不是"先把框架搭好再说"。

## 9. 还没想清楚的问题

诚实列出来，不假装都定了：

1. **catalog 多大合适**：现在假设几十 KB。几百个游戏时会不会太大？需要分页吗？
2. **多源的冲突**：两个源有同一个游戏（同 id 不同版本），显示哪个？现在的答案"先配置的优先"，但玩家可能想看新的。
3. **局域网发现**：能不能自动发现同一网段的源（mDNS）？这样不用手输 IP。
4. **安装进度能不能暂停**：大包下载中断了，下次能不能续传？
5. **游戏之间共享素材**：两个游戏用同一套素材，要不要去重？现在不打算做，因为复杂度高收益低。
6. **Tauri 的更新回滚**：如果新版本 exe 起不来，怎么自动退回旧版？这一块没设计。

前四个在 M2-M5 期间会自然有答案。后两个需要专门设计。
